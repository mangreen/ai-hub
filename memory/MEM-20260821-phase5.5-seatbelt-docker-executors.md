# MEM: Phase 5.5 — Seatbelt/Docker executor 研究與實作
Date: 2026-08-21
Tags: [sandbox, seatbelt, docker, sbpl]

## Summary
實作了 `ctx.sandbox` 的兩個具體 executor：Seatbelt（macOS）跟 Docker（新增，
非原計畫）。E2B 雲端 executor 延後。160 個測試全過（135 舊的 + 25 新的）。

## Details

**先更正上一輪自己講錯的話：** Phase 4 完成時的 todo.md 寫「Phase 5.5 需要先有
tool calling」，這個講法不精確。`SandboxExecutor.execute(request)` 是通用的
「執行一個指令、回傳結果」介面，建造跟驗證這個介面的具體實作，跟「應用程式裡誰
會呼叫它」是兩件獨立的事——tool calling 只決定「`task-graph` 執行到某個 node
時要不要把它的動作路由進 sandbox」，那是**接線**的問題，不是 executor 本身能不能
成立的問題。這次直接動手做 executor，接線留給 tool calling 真的設計出來再做。

**Seatbelt profile 設計查證來源：** Anthropic 自己的 production 專案
`anthropic-experimental/sandbox-runtime`（透過 DeepWiki 查證，非猜測）——
它也是用 `sandbox-exec -p <profile>` 這個 CLI 模式，profile 結構是
「`(deny default)` → 明確 allow-list → 針對危險路徑的強制 deny，即使在
allow-list 範圍內」。這個「allow-list + 例外強制 deny」的順序**很重要**：
`(deny default)` 已經擋掉所有東西，所以不需要再手動寫
`(deny file-write* (subpath "/"))`；只要 `(allow file-write* (subpath
workspaceDir))` 開一個洞，再用 `(deny file-write* ...)` 針對這個洞裡的危險
子路徑（`.git/hooks`、`.git/config`）縮小回去就夠了——這是從 Anthropic 的
實作裡學到的、比我自己一開始想的版本更簡潔的寫法。

**這台開發機是 Linux，`sandbox-exec`/`docker` 都不存在，兩個 executor 都無法
實際執行驗證：** 只能驗證兩件事——(1) 純函式建構的指令/profile 內容對不對
（`buildSeatbeltProfile`/`buildDockerArgs`，字串/陣列比對，完全跟平台無關）、
(2) `execute()` 呼叫 `spawnImpl` 時傳的指令名稱/參數/選項對不對（injectable
spawn，跟 Phase 3 的 injectable fetch 同一個套路）。**無法驗證的是「隔離真的
擋得住」這件事本身**——寫了兩支腳本 `scripts/verify-seatbelt.ts`/
`scripts/verify-docker.ts`，要在真正有 `sandbox-exec`/Docker 的機器上跑
`pnpm verify:seatbelt`/`pnpm verify:docker` 才能證明。`isAvailable()` 倒是
可以在這台機器上真的測（Seatbelt 測 `process.platform !== 'darwin'` 正確回
`false`；Docker 測「spawn 失敗要回 `false` 而不是 throw」——這部分不需要真的
有 docker binary，用 injectable spawn 模擬 ENOENT 錯誤即可驗證邏輯對不對，
跟「真的有沒有裝 Docker」是分開的兩件事）。

**Docker Desktop 4.12.0（Engine 20.10.17）為什麼夠用：** `--network none`、
bind mount（`-v`）、`--memory`/`--cpus` 都是 Docker Engine 很早期（2016-2017
年）就穩定的功能，不需要新版才有。CLAUDE.md Section 0 原本記錄的「Docker
Desktop 不支援 Big Sur」，前提是「要重新裝新版」，既有的舊版安裝不受影響——
這次確認了這件事，不用再去碰 Colima/OrbStack。

**E2B 為什麼這次沒做：** 上一輪已經查過 `e2b` npm package 的表面用法
（`Sandbox.create()`、`sandbox.commands.run()`），這次額外確認了
`npm install e2b` 不會觸發任何 native binary 編譯（乾淨的純 JS/TS 依賴，
符合本專案一貫原則）。沒做的原因是**範圍**，不是技術問題：沒查到它底層的
wire protocol（HTTP 還是 gRPC、確切的 request/response 格式），要嘛用官方
SDK 當黑盒子依賴（可以做，但還沒決定要不要），要嘛自己重寫底層協定（沒有
把握做對）。留到真的需要「不管在哪台機器都能跑的保底選項」時再決定走哪條路。

## When to Use
之後如果要幫任何「本地執行環境限制」的功能寫測試，先想清楚「這個環境本身的
邏輯」（純函式，任何機器都能測）跟「跟真實系統互動的部分」（injectable I/O，
測呼叫形狀）該怎麼切，跟這次 Seatbelt/Docker 的做法一致。如果真的需要驗證
「在特定作業系統/工具鏈上實際行為對不對」，寫一支獨立的驗證腳本，誠實標注
「這個專案的開發環境驗證不了這件事」，不要假裝測試綠燈就等於行為正確。
